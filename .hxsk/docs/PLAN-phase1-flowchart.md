## 3. 시나리오별 개입 흐름

### 시나리오 A: 에이전트가 파일을 읽지 않고 편집하려 할 때

```
에이전트: "이 파일 내용을 이미 알고 있으니 바로 수정하자"
                │
                ▼
     ┌─ Layer 1: Iron Law "NO EDIT WITHOUT READ FIRST" 인식
     │  └─ 프롬프트 레벨에서 자기 차단 시도
     │
     ├─ (thinking 부족으로 Iron Law 무시한 경우)
     │
     ▼
     ┌─ Layer 2: 합리화 테이블 "이미 안다 → 수정됐을 수 있다"
     │  └─ 스킬 로딩 시 합리화 인식
     │
     ├─ (합리화 테이블도 무시한 경우)
     │
     ▼
     ┌─ Layer 3: PreToolUse 훅 read-before-edit.py
     │  └─ read-history.log에 해당 파일 없음 → ⚠️ 경고 반환
     │  └─ 에이전트가 경고를 보고 Read 먼저 실행
     │
     ▼
     결과: 3중 방어 중 최소 하나가 차단
```

### 시나리오 B: 에이전트가 검증 없이 "완료" 선언하려 할 때

```
에이전트: "코드를 수정했으니 완료입니다"
                │
                ▼
     ┌─ Layer 1: Iron Law "NO COMPLETION WITHOUT VERIFICATION"
     │  └─ 프롬프트 레벨에서 Gate Function 진입
     │
     ▼
     ┌─ Layer 2: Gate Function 5단계
     │  1. IDENTIFY — "npm test로 증명"
     │  2. RUN — npm test 실행
     │  3. READ — 출력 확인
     │  4. VERIFY — 0 failures 확인
     │  5. CLAIM — "테스트 통과, 완료"
     │
     ├─ (Gate Function 건너뛴 경우)
     │
     ▼
     ┌─ Layer 3: Stop 훅 post-turn-verify.sh
     │  └─ 응답에 "완료" 포함 + Bash 실행 이력 없음 → ⚠️ 경고
     │
     ▼
     결과: 프롬프트 또는 인프라에서 차단
```

### 시나리오 C: 아키텍처 결정이 필요한 복잡한 작업

```
사용자: "인증 시스템을 JWT에서 세션 기반으로 마이그레이션해줘"
                │
                ▼
     ┌─ Layer 1: CLAUDE.md Thinking Budget 참조
     │  └─ "아키텍처 결정 → 깊은 추론 필요" 인식
     │
     ▼
     ┌─ Layer 2: Ultrathink 트리거 조건 매칭
     │  └─ "3+ 모듈 영향" + "보안 관련" → 필수 트리거 2개 해당
     │  └─ 깊은 thinking으로 임팩트 분석
     │
     ▼
     ┌─ Layer 4: CSO — impact-analysis 스킬 정확히 매칭
     │  └─ description: "Use when changes affect 3+ modules..."
     │  └─ 전체 SKILL.md 로딩 → 체계적 분석
     │
     ▼
     결과: 충분한 추론 → 정확한 스킬 선택 → 체계적 실행
```

### 시나리오 D: 기존 파일을 Write로 덮어쓰려 할 때

```
에이전트: "전체 파일을 새로 작성하는 게 빠르겠다"
                │
                ▼
     ┌─ Layer 1: Iron Law "NO WRITE TO EXISTING FILES"
     │  └─ "기존 파일 수정은 Edit 사용" 인식
     │
     ▼
     ┌─ Layer 2: 합리화 테이블
     │  └─ "덮어쓰기가 빠르다 → 다른 변경을 날린다. Edit을 써라"
     │
     ▼
     결과: Write 대신 Edit 사용
```

## 4. 기존 훅 생명주기와의 통합

```
SessionStart
├─ session-start.sh: STATE.md + git status 주입
├─ read-history.log 초기화 (신규)                    ← (6) 연계
│
▼ [작업 수행]
│
├─ PreToolUse
│   ├─ file-protect.py: .env/시크릿 보호 (기존)
│   ├─ bash-guard.py: 파괴적 명령 차단 (기존)
│   └─ read-before-edit.py: Read 이력 확인 (신규)    ← (6)
│
├─ PostToolUse
│   ├─ auto-format.sh: 자동 포맷 (기존)
│   ├─ track-modifications.sh: 변경 파일 추적 (기존)
│   └─ read-history 기록 (신규/기존 확장)             ← (6) 연계
│
├─ Stop
│   ├─ post-turn-verify.sh: 작업 검증 (기존 + 확장)  ← (7)
│   └─ stop-context-save.sh: 세션 컨텍스트 저장 (기존)
│
├─ PreCompact
│   └─ pre-compact-save.sh: 스냅샷 (기존)
│
├─ SubagentStop
│   └─ (prompt): 결과 요약 (기존)
│
▼ SessionEnd
├─ save-transcript.sh: 대화 내역 저장 (기존)
└─ save-session-changes.sh: 변경사항 저장 (기존)
```

## 5. 리뷰 체크리스트

### 설계 정합성
- [ ] Iron Laws가 AGENTS.md L1 제약 규칙에 부합하는가? (3줄, 정책 수준)
- [ ] 합리화 테이블이 기존 Forbidden Phrases의 자연스러운 확장인가?
- [ ] Gate Function이 기존 4단계 Protocol의 5단계 강화인가?
- [ ] Ultrathink이 CLAUDE.md ≤120줄 제약을 지키는가? (3줄 참조)
- [ ] CSO가 기존 description 패턴을 깨뜨리지 않는가?
- [ ] 신규 훅이 기존 훅 생명주기에 자연스럽게 통합되는가?
- [ ] 에이전트 정의 파일 변경이 불필요한가?

### 이중 방어 완전성
- [ ] Iron Law #1 (Read before Edit) → PreToolUse 훅 (6) 이중 방어
- [ ] Iron Law #2 (Verify before Claim) → Stop 훅 (7) 이중 방어
- [ ] Iron Law #3 (Edit not Write) → 프롬프트 단독 (기존 file-protect와 부분 중복)

### 부작용 검토
- [ ] read-history.log가 대용량 세션에서 성능 문제를 일으키지 않는가?
- [ ] Stop 훅 경고가 false positive를 과다 생성하지 않는가? (중간 보고 vs 최종 완료)
- [ ] CSO 변경이 기존 스킬 트리거를 깨뜨리지 않는가?
