## 정보이론적 프레임워크

프로그램을 **압축 가능한 정보**로 사고. 최소 기술 길이(MDL) 원칙 적용.

## 핵심 원리: 의존성 길이 최소화 (Dependency Length Minimization)

```
관련 항목을 가깝게 배치 → 의존성 거리 감소 → 엔트로피 감소 → 버그 감소 + 일반화 향상
```

**압축 알고리즘과의 관계**: 관련 항목이 가까울수록 역참조 오프셋이 작아져 더 적은 비트로 표현 가능 = 높은 압축률.

## 코드 설계 시사점

**Go 언어의 의존성 최소화 설계**:
- 예외 제거: 원거리 catch 블록 점프 제거
- `defer`: 리소스 정리를 관련 위치로 복원
- `:=` vs `=`: 광범위 상태 수정 실수 방지
- 소문자/대문자: 전역 변수 범위 1비트로 제어

**John Carmack의 인라인 원칙**:
> "인라인 코드는 엔지니어를 '현재 수행 중인 행동의 전체 공포'에 끊임없이 인식시킨다"

## 과적합(Overfitting) 방지

> "필요한 지식을 초과하는 비트 사용은 일반적으로 과적합과 열악한 일반화로 이어진다"

- 분 단위 타임스탬프를 단순 날짜에 사용 → 엣지 케이스 버그 발생
- 필요 이상으로 복잡한 타입 → 불필요한 상태 공간 확장

## 두 종류의 "버그"

| 유형 | 정의 | 해결책 |
|------|------|--------|
| **실제 버그** | 사양 미준수 구현 | 테스트/QA 증대 |
| **불완전성 버그** | 올바른 구현이지만 사양이 불충분 | 개발 속도 향상 (더 많은 케이스 커버) |

두 해결책은 거의 **반대** — 하나에 치중하면 다른 쪽이 악화.

## 조기 모듈화의 위험

> "조기에 컴포넌트 분리를 모방하는 것은, 높은 도메인 전문성 없이 잘못된 추상화로 이어진다"

- 부정확한 추상화 → 잘못된 가정 고정화
- 코드베이스도 B-트리처럼 **지속적 재균형** 필요
- 도메인 지식 축적에 따라 점진적으로 구조 진화

## LLM과의 관계

- 어텐션 메커니즘 = 의존성 트리 정렬 메커니즘
- 의존성이 멀수록 LLM이 참조 따라가기 어려움
- **의존성 최소화 = LLM 친화적 코드**
- RAG 필요성 = 의존성이 먼 정보를 가까이 가져오는 것

## 실용적 결정 기준

코드 분리(DRY) 시 확인:
1. 전체 로직 + 테스트 크기가 실제로 감소하는가?
2. 의존성 길이 증가 비용은?
3. 광범위 제네릭 함수가 수정을 어렵게 만드는가?
